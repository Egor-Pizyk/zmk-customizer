# ZMK Customizer Constitution

## Core principles

The normative principles and rationale are in [docs/principles.md](../../docs/principles.md). This compact projection is consumed by Spec Kit; it introduces no independent policy.

1. Correct output over features: generator changes require independent golden contracts.
2. Domain first: business rules are pure domain operations; UI renders and dispatches.
3. Static only: no backend, runtime network or telemetry; work offline after load.
4. Untrusted data: storage validates imported/persisted data and preserves the current project on failure.
5. Explain ZMK options: user-facing options carry descriptions and pinned-version documentation links.
6. Minimal code: no speculative abstractions, folders or configuration.
7. Deterministic output: the same project produces identical generated bytes.
8. Accessible: controls are labeled and keyboard reachable; canvas operations have keyboard/table alternatives.

## Constraints and gates

- Target ZMK v0.3.0; no main-only output or UI options. Read relevant verified notes before changing syntax.
- [Architecture](../../docs/architecture.md) owns the exact dependency matrix and exceptions; do not replace it with a simplified layer chain.
- [Tooling](../../docs/tooling.md) owns approved dependencies; new runtime dependencies require an ADR.
- [Workflow](../../docs/workflow.md) owns change routes, tests-first requirements, stage gates and traceability.
- [Commands](../../docs/commands.md) owns completion checks by change type; [testing](../../docs/testing.md) owns behavioral verification.
- Load applicable guideline sections lazily through `AGENTS.md` when needed for the next decision/edit; no startup document batch.

## Governance

`AGENTS.md` routes to the normative documents above. Change a rule in its owning document first and update this projection in the same change if affected. Resolve disagreement explicitly; do not treat this projection as a second source of truth.

Version amendments: MAJOR for incompatible principle changes, MINOR for materially expanded constraints, PATCH for wording/synchronization. Spec analysis checks applicable principles and gates before implementation. Do not run constitution generation for every feature.
