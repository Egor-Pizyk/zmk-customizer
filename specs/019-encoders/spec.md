# Feature Specification: Rotary encoders

**Feature Branch**: `019-encoders`
**Created**: 2026-10-19
**Status**: Implemented; automated verification passed; manual accessibility checklist remains open (see verification.md)
**Input**: Next roadmap feature: rotary encoders (019).

## Goal and scope

Add EC11 rotary encoders to a custom keyboard, configure their wiring and rotation response, and download a ZMK v0.3 configuration that includes them.

**In scope**: Encoders with editable layout position, half, A/B GPIO pins, electrical steps per rotation and action triggers per rotation; per-layer clockwise/counterclockwise actions; validation, persistence, undo/redo and export.
**Non-goals**: Other sensor types, encoder push buttons as special entities, lighting, live hardware input and firmware flashing. Feature 036 item 1 later links an optional ordinary key to an encoder; it does not introduce a special switch entity.
**Existing contracts to preserve**: Existing project files, key wiring and bindings, deterministic exports without encoders, immutable editing and keyboard access.

## User scenarios and acceptance

### US1 — Configure encoder hardware (P1)

1. Given a keyboard, adding an encoder shows a numbered layout marker and labeled hardware controls. Position, half, pins and both rotation counts can be changed using the keyboard. Each applied edit is one Undo step; Redo restores it.
2. Given an unassigned, unavailable or already used pin on the same half, a readable Schematic problem identifies the encoder and control. Export remains blocked until repaired. Identical pin numbers on different halves are allowed.
3. Given a controller family change, incompatible encoder pins are cleared and reported for reassignment; same-family supported assignments survive. Switching split to unibody reports any right-half encoder until repaired.

### US2 — Choose rotation actions per layer (P1)

1. Given two layers and two encoders, clockwise and counterclockwise actions can differ independently for every encoder and layer. Reordering or deleting keys does not change their targets; reordering layers keeps their actions.
2. Given an encoder with no assigned actions, turning it does nothing. Deleting an encoder removes only its rotation assignments; Undo restores hardware and all layer assignments.
3. Given a deleted layer, behavior or macro referenced by a rotation action, Bindings reports the reference and provides a keyboard reachable repair control.

### US3 — Save and export (P1)

1. Save/open and browser reload preserve all encoder hardware and layer actions. Older files open with no encoders and retain their original content.
2. For unibody, generated files contain enabled EC11 hardware and ordered sensor bindings. For split, shared sensor order is identical on both halves and each encoder is enabled only on its own half. Required driver configuration is included for every half with an encoder.
3. Invalid encoder data blocks export. Malformed imported structures leave the current project untouched. A keyboard without encoders retains the previous generated bytes.

## Requirements

- **FR-001**: Add, edit and delete up to 16 encoders with stable identities, layout positions and left/right half assignments (US1).
- **FR-002**: Configure independent A/B connector pins, positive whole electrical steps per rotation and positive whole triggers per rotation; explain both counts and link pinned documentation (US1).
- **FR-003**: Detect missing/unsupported/reused pins across encoders and existing switch wiring on the same half, invalid counts and positions, and right-half encoders on unibody keyboards; route issues to the responsible controls (US1).
- **FR-004**: Independently assign clockwise and counterclockwise actions on each layer, including existing key, layer, behavior and macro actions; missing assignments mean do nothing (US2).
- **FR-005**: Preserve identity through key/layer edits; deletion removes the encoder's assignments; referenced deleted action targets remain visible and block export (US2).
- **FR-006**: Persist encoder content, migrate older files, reject malformed structure safely and preserve one-step history for each edit (US1–US3).
- **FR-007**: Generate deterministic v0.3 EC11 nodes, per-sensor trigger settings and matching per-layer sensor bindings, with half-local activation and required driver settings; zero encoders produce unchanged output (US3).
- **FR-008**: Expose all editing through labeled keyboard reachable controls with inline issues, pinned docs links, repair navigation and a layout marker (US1–US2).

## Edge cases

Two channels on the same pin; pins shared with manual wires or wiring terminals; right-only split encoder; different rotation counts for multiple encoders; empty keyboard; deleting the last encoder; deleted references in an inactive layer; unsupported controller pin after import; invalid numeric values remain repairable; oversized and duplicate imported identities; undo followed by a new encoder edit clears Redo.

## Key entities

Encoder: stable identity, layout position, half, two GPIO assignments and two rotation counts. Rotation binding: encoder identity and clockwise/counterclockwise actions, owned by a layer.

## Success criteria

- **SC-001**: A user can configure two encoders on opposite halves and distinct rotation actions on two layers using only keyboard controls.
- **SC-002**: Save/reload and Undo/Redo restore exact encoder content and assignments in all acceptance scenarios.
- **SC-003**: Independent upstream encoder fixtures and generated golden files agree on sensor ordering, pins, activation and driver settings; generated unibody and split fixtures compile for v0.3.
- **SC-004**: Every introduced invalid-state category blocks download and links to a repair control; no-encoder output remains byte-identical.

## Assumptions and open questions

EC11 is the supported hardware family. Defaults are 80 electrical steps and 20 triggers per rotation, matching upstream Sofle; action defaults are do nothing. Electrical steps are 1–360 and triggers per rotation are positive divisors of 360, avoiding runtime arithmetic limitations in pinned v0.3, positions use existing physical-layout numeric bounds. Encoders use numeric position controls and a layout marker rather than introducing another drag tool. The push switch remains an ordinary key. No material open questions remain.
